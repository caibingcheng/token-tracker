# AI Gateway 代理链路（核心）

> 上级文档：`AGENTS.md`。改 `/v1/*` `/v1beta/*` `/raw/*` 代理链路前必读。

- **路由**：`src/routes/v1/[...path]/route.ts` + `src/routes/v1beta/[...path]/route.ts` + `src/routes/raw/[...path]/route.ts`（文件里的 `runtime = "nodejs"`、`dynamic = "force-dynamic"` 导出对 Hono 无效，历史保留）
- **裸透传入口 `/raw/*`**：客户端打 `/raw/<upstream base URL 之后的部分>`，`stripRawPassthroughPrefix()`（`src/lib/gateway/proxy.ts`）剥掉 `/raw` 前缀得到内层 path（内层再过一次 `sanitizePathSegments` 防 `..` 逃逸；内层为空或逃逸 → 400 `invalid_request_error`（裸 `/raw` 进不到 handler，由 Hono 路由层 404，与 `/v1` 一致）），后续协议检测 / model 提取 / 路由 / 配额 / failover / session 粘性 / 转发全部复用同一套逻辑，转发用内层 path（上游永远看不到 `/raw`）。用途：`/v1`、`/v1beta` 之外的上游端点，如 OpenRouter（`base_url=https://openrouter.ai/api`）的 `POST /alpha/decisions`（上游真实 URL `https://openrouter.ai/api/alpha/decisions`）—— 协议落 openai（注入 `Bearer`）、model 取 body.model、usage 为 responses 风格由 openai parser 归一化。**内层 path 直接拼在 upstream `base_url` 之后（只对 `/v1`、`/v1beta` 前缀 dedup）**：`base_url=https://openrouter.ai` 时客户端打 `/raw/api/alpha/decisions`，`base_url=https://openrouter.ai/api` 时打 `/raw/alpha/decisions`；两者不匹配会拼成 `/api/api/...` 被上游 404。认证层 `src/server/verify-session.ts` 只拦 `/api/*`，`/raw` 不受影响；认证走网关 proxy 内既有虚拟 key 逻辑（**不是** `withAuth`，那是 `/api/*` 管理路由的要求）。已知边界：`GET /raw/.../models` 仍被「`GET /v1/models` 并集」短路，非 POST/PUT/PATCH/DELETE 方法一律 405
- **核心逻辑**：`src/lib/gateway/proxy.ts`（纯逻辑可单测）；依赖注入 `src/lib/gateway/proxy-deps.ts`（DB 访问；session/health 为**模块级单例**，因 `createProxyDeps()` 每请求创建）
- **命名路由（named route，替代自动路由 + 可选分类器）**：`named_routes` 行（name+protocol 唯一，含 instruction + classifier 指向 + enabled）自带目标池 `named_route_targets`（`UNIQUE(named_route_id, upstream_id, upstream_model)`，每条含 **description** 特性描述 + priority）。目标分两种：带 provider 的目标 = upstream + 真实模型名（单 hop）；**不带 provider 的目标（`upstream_id` NULL，auto 目标）= 只写模型名，经 `expandNamedRouteTargets()` 展开**：模型名先按命名路由精确匹配（**嵌套**，enabled、同协议），命中则递归展开该路由目标池（其 pool 按 priority 静态排序，**不调用其 LLM 分类器**——分类器是请求上下文决策，嵌套展开是静态解析；防环 = 展开路径 visited 路由 id 集合，循环引用跳过该目标）；未命中走自动路由候选池（exact > wildcard、priority 升序、按 upstream 去重），多 provider 同名 model 自然展开成多 hop failover 子链。`findNamedRoute()` 命中后目标池按 priority 升序（同 priority 按 id）排序、各自展开成 hop；**target 的 upstream family 与 route protocol 有意不解耦**（管理员显式配置，允许跨 family 选 target，如 relay 同时接受多种风格；配错由运行时 404/failover 暴露，写入侧不再 400，UI 选项对不一致家族加标注提示）；禁用/不存在的 upstream 目标跳过；健康目标排链首、unhealthy / model 级不可用目标排尾（兜底），兜底 2xx 走统一自愈（degradedUpstreams 集合 + markHealthy/markModelHealthy）；body/path 改写 **per-hop 按当跳目标计算**（OpenAI/Anthropic 改 body.model、Gemini 改 path 模型段），写库 model = 成功落点目标的真实名，响应 model 回写虚拟名；多目标时 session 粘性生效（**目标粒度决策、hop 粒度匹配**：分类器/binding 选中的是目标条目，binding 存展开后具体 hop 的 `upstreamId + targetModel`，预选时反查该跳属于哪个目标）；同名自动路由完全失效（UI 标注 `overridden`）；**无有效目标（池空或全部目标解析不出 hop：upstream 全失效 / auto 名不可解析 / 嵌套成环）时 502 `named_route_unavailable`**（不回退自动路由）。要点：
  - **分类器种类**（`named_routes.classifier_kind`）：`'priority'`（缺省）= **规则分类器**——按优先级 + 可用性选链首（首个健康目标），零 LLM 开销（不配分类器的命名路由即此形态）；`'model'` = LLM 分类器（见下）。仅 1 个目标时跳过分类器（链首即该目标）
  - **决策时机**：每 session 首请求一次（无 route 粒度 binding 时）；session binding 为 `(upstreamId, targetModel)` 粒度，决策/回退结果均写 binding，整个 session 不变；路由内 failover 落点与决策目标漂移时重绑
  - **分类器配置**：命名路由的 LLM 分类器**任选 upstream + 模型**（写入侧只校验 upstream 存在；UI = provider 下拉 + 可编辑模型 selector）。**未声明的模型一律按 `jev-systemone` 决策模型处理**：`src/lib/gateway/proxy.ts` 查 `upstreams.classifier_models`（JSON `[{model, type, maxInputTokens?, path?}]`）命中已声明条目则照旧生效（存量 `chat` 声明保留，且仍要求 openai 协议 upstream），未命中合成 `{model, type:'jev-systemone'}` 条目。type 决定 wire format（adapter 注册表：`jev-systemone` = POST /v1/systemone typed choice 题，criteria=map<选项键 r\<routeId\>, description>；`chat` = openai chat completions）；**upstream.protocol 决定认证/传输**（Bearer/x-api-key、proxyUrl、redirect manual），两者正交；已声明条目的 `path` 覆盖端点（OpenRouter 为 /alpha/decisions）；新增分类协议 = 加 adapter（`buildRequest`/`parseResponse` 两函数），主链路零改动；upstream UI 不再管理 classifier_models 声明（列保留，API 读写兼容）
  - **分类器调用**：`src/lib/gateway/classifier/` 直连 classifier upstream（不经 handleProxyRequest，防递归），10s 超时、全 key 链尝试、redirect manual；**预算制摘要**（`summarize.ts`）：输入预算 = 条目 maxInputTokens（写入侧上限 1M）> models.dev context window（**派生预算封顶 32k**，防大 context 模型一次决策发巨量 summary）> 默认 4096，扣固定开销后 chars/4 估算 + 20% 安全边际，首条 user（身份锚点，至多一半预算）+ 由新到旧贪心装填，system 不送
  - **回退**：分类器不可用/输出非法/未配置 → priority 最小 route 排链首（不阻塞流量）
  - **usage**：分类器消耗记一条 `status='classifier'` 记录（model=分类器真实名，request_model=虚拟名）；主请求记真实落点（与无分类器命名路由同口径）
  - hop 改写为 rule 粒度（hop 自带 targetModel），同 upstream 挂多 targetModel 无引用冲突
- **流程**：path `..` 段净化（`sanitizePathSegments`，逃逸出 base 前缀 → 400）→ 提取虚拟 key（**仅 header**：Authorization Bearer / x-api-key / x-goog-api-key；`?key=` query 认证已移除 —— query 会进访问日志/反代日志/Referer/浏览器历史；转发前仍会剔除 `key` query 参数，防客户端把 key 混在 query 里透给上游）→ 校验（**全表解密比对**，AES-256-GCM 随机 IV 无法索引）→ 提取 model（OpenAI/Anthropic 取 body，Gemini 取 path；**长度上限 256**）→ `routeModelByProtocol()` 取候选（精确 > 前缀通配，priority 小者胜，协议过滤）→ **配额检查**（`checkQuota`，`src/lib/gateway/quota.ts`：max_rpm/max_tpm/max_daily_tokens/max_monthly_tokens 任一超限 → 429 `quota_exceeded`，不转发上游）→ **跨 upstream 故障转移链**（session 粘性 binding 优先 → 其余 healthy 候选按 priority；每个 upstream 内遍历 key、每个 key 内 `MAX_RETRY=2`，**401/403 认证错误不重试直接换 key/upstream 并触发 failover**，其余 4xx 直接透传不重试、不触发 failover，**3xx 重定向一律视为失败（`redirect: "manual"`，防上游 key 跨源泄露）**，**流式输出开始后不可重试**；某 upstream 全部 key 失败标记 unhealthy 并继续下一个；**无健康候选时兜底**：自动路由/命名路由/responses 辅助端点均在全部候选不健康时回退尝试**未 givenUp** 的 unhealthy 候选（没有剩余可尝试候选则 502），**兜底拿到 2xx 立即 markHealthy + markModelHealthy 自愈**）→ 透传（剥离认证头 + 客户端可控源信息头 + `accept-encoding: identity`，按协议注入真实 key）→ 响应管道边透传边增量解析 usage → `withSkipCache` 写库
- **Session 粘性**：请求进入主链后只解析一次会话 ID——原生 header 优先（`x-claude-code-session-id` / `x-opencode-session` / `session-id` / `x-session-id` / `session_id` / `x-session-affinity` / `x-conversation-id`），缺失才由 `src/lib/gateway/session.ts` 计算 `sha256(system 拼接尾部 1024 + 首条 user 文本前 1024 + model + vkId + protocol)`；Records、路由粘性与出站 `${var.sessionId}` 共用解析结果，原生 ID 用于路由时再按 model/vkId/protocol 派生作用域 key；内存 LRU（max 5000 / ttl 24h），仅 failover 落点 ≠ 默认 upstream 时保存 binding；命名路由 binding 为展开后具体 hop 的 `(upstreamId, targetModel)`（auto 目标 = 展开落定的 upstream），**named-route binding 必带 targetModel**——`targetModel=undefined` 是旧自动路由粒度的残留，命名路由匹配时忽略（不通配）；预选 = binding 反查目标池展开链内的一跳；分类器决策/回退结果在请求成功前即写 binding（防分类器持续失败每请求白付超时）；binding 失效条件：upstream 被禁用/无 key/协议不匹配/不 healthy/不再匹配 model（链过滤自动覆盖）；单目标跳过 binding 查询与分类器调用；**落库 `session_id` 复用同一请求级解析结果**：原生 header 原值优先，未携带且 body 带非空 `messages` 时回退该指纹（`/raw` 等无 messages 的端点不造假 id，保持 NULL）
- **健康状态**：`src/lib/gateway/health.ts`（内存缓存 + **DB 持久化**：upstream 级存 `upstreams.health_status`，model 级存 `upstream_model_health`，重启后懒加载恢复探活调度）+ `src/lib/gateway/probe.ts`（非流式小请求探活，不记 token）；**upstream 2xx 自愈 / 重新启用 disabled→enabled 均回到首档；档位纯内存，重启归零后从 30s 重探；探测 model 选择：`upstreams.health_check_model` 优先，否则 `enabled_models` 第一个非通配，无则保持 unhealthy）；**放弃兜底**：末档（30min）内再连续探活失败 `PROBE_GIVE_UP_FAILURES`=4 次（自首次故障约 2h06m，不含探活自身耗时）→ `isGivenUp`，该 upstream 从**兜底候选**里剔除（死透的 upstream 在兜底里只会白等超时：非流式每个 key 最长 60s×`MAX_RETRY`，多 key 累加），定时探活照旧每 30min 跑；**清 givenUp 的途径 = 探活或 Probe now 或 Test 成功（经 `markHealthy`，同时恢复健康）/ PATCH `enabled=true`（`resumeProbing`，不要求发生 `false→true` 转换，只重置内存档位与 givenUp，不改健康状态；仍 unhealthy 时随后立即 probeNow，成功才恢复健康）**；givenUp 纯内存（重启归零，重启后死透 upstream 重新获得兜底资格，需再累计约 2h06m 才再次被剔除）；UI probe 文案显示 `given up`；**全候选均 givenUp 的错误码**：主链与 responses 辅助链均 502 `upstream_unavailable`（不发任何上游请求），命名路由目标池被清空则 502 `named_route_unavailable`；**givenUp 的过滤时机**：命名路由在分类器/预选**之前**剔除（不为必然被丢的目标付 LLM 成本），自动路由在候选池组装后剔除；**探活全 key 链**：`probeUpstream` 用 `probeModelWithKeys` 逐个 key 探测（与真实请求/手动 test-model 同口径），任一 key 成功即恢复；**404 放宽**：全部 key 均 403/404（`sawModelError && !sawAuthError`，上游可达 + key 有效，仅探测 model 被下架/改名）→ 视为 upstream 级恢复，**401 不放宽**；探活恢复时顺带 `markModelHealthy` 清**被探测的那个 model** 的标记（与兜底自愈「清当跳 + 下次倒计时 + **Probe now** 按钮（`POST /api/admin/upstreams/[id]/probe`，不要求 enabled、不记审计，与 test-model 手动测试同口径；`HealthTracker.probeNow` in-flight 互斥防并发重入）；**生命周期联动**：PATCH `enabled=false` → `stopProbing`（停 embedding 模型混用配这个即可，不用再拆同 base_url 条目；认证头仍按 `upstream.protocol` 注入（本特性只管端点+body，不含 per-model 协议覆盖），通配 enabled_models 条目不走 per-model 匹配
- **写库**：仅 2xx 响应记录；响应无 usage 时先估算兜底（`src/lib/gateway/estimate.ts`），估算口径：非 ASCII 1 字 ≈ 1 token、ASCII 4 字 ≈ 1 token（流式按整段响应累计字符后统一取整，不逐 delta 取整）；input 对请求 `messages` / `contents`（OpenAI responses 风格为 `input`）的 JSON 序列化估算（**>1MB 请求走字节跨度估算** `estimateInputTokensFromSpans`，不物化消息树，紧凑 JSON 下与序列化口径逐字节平价），非流式 output 只对提取的 assistant 文本估算，流式 output 按流内内容增量累计字符估算（thinking/reasoning 与 tool_calls 参数不计入，会低估；多模态 Base64 内容按文本计入，会高估）。**触发条件**：未解析到 usage、响应 body 已完整读完（`responseComplete`）、未标记中断，流式与非流式均适用；估算 `input + output > 0` 记 `status='estimated'`，否则记 `status='no_usage'`。**`estimated` 行的 `cache_read` / `cache_write` 恒为 0**（估算 input 全部落在 `input_tokens`），这些 token 照常计入聚合与派生成本，但不代表真实用量，cache 指标无法反映该请求的真实缓存消耗。中断（`client_aborted` / `stream_interrupted`）不估算、保持中断 status。`status`/`latency_ms` 为新增列。**口径约定**：`input_tokens` 字段统一按不含 cache_read 写入（OpenAI/Gemini 在 parser 层做减法），`cache_read` 单独列示，展示层 Total Input 含 cache。**model 列写真实名**（路由重写时用 targetModel，否则用请求名），原始请求名写 `request_model`（虚拟名路由可追溯）。
- **流式 usage 增量解析**：`src/lib/gateway/proxy.ts` 透传时用 `StreamUsageExtractor`（`parsers/stream-usage.ts`）边读边解析，只保留首尾 usage 小对象，**不持有完整响应体**（内存 O(1)）；流式空闲超时默认 30min，由 settings 表 `stream_idle_timeout_minutes` 配置（Security tab，无 env），超时中断流并释放连接。`POST /v1/chat/completions` 且 `stream === true` 时，若 `stream_options.include_usage` **未显式出现**（`hasOwnProperty` 判定，显式 `true` / `false` / 非法值均保留不覆盖，非法值交上游校验）则注入 `true`；否则上游/中转可能不在流里发 usage chunk，此时在响应完整读完后尝试估算兜底，估算合计非零记 `estimated`，仍估不出才记 `no_usage`。非流式仍整包缓冲，但**不整包 parse**：usage 取顶层 `usage`/`usageMetadata` 区间切片后局部 `JSON.parse`（`json-scan.ts` 线性扫描；响应字节只拼接一次、仅估算兑底时才 decode）；model 回写同样按顶层区间切片（`rewriteModelNonStreamingBytes`），大响应零树化。
- **模型并集**：`GET /v1/models` 返回所有启用上游 `enabled_models` 中非通配条目

  - `GATEWAY_SECRET` 缺失时代理路由与 admin API 返回 503，不静默降级（`proxy-deps.ts` 的 `GatewaySecretMissingError` 向上传播，不再吞错降级 401/502）

  - **管理端旁路 fetch 同样 `redirect: "manual"` + 受保护 dispatcher**：`fetchUpstreamModels`（upstream-client.ts）、探活 `probeOnce`（probe.ts）、余额 `fetchBalance`（balance.ts）、分类器（classifier/index.ts）、同步推送（sync/pusher.ts）均带真实 key 访问第三方上游，3xx 一律视为失败（防 key 经跨源重定向被动泄露），且必须走 `getOutboundDispatcher()`（连接时地址校验），与主代理链路 `proxy.ts` 口径一致
  - **Upstream 级 HTTP CONNECT 代理（`proxy_url`）**：仅 `http://`/`https://` 代理（undici `ProxyAgent`），CONNECT 隧道 TLS 端到端，API key 对代理不可见；`proxy_url_encrypted` 走 AES-256-GCM 加密落库（写后不可读，GET/审计仅回显脱敏 `scheme://host[:port]`）；六处出站 fetch（主链、responses 辅助链、probe、fetchUpstreamModels、fetchBalance）统一 `...(dispatcher ? { dispatcher } : {})` 注入（`src/lib/gateway/proxy-dispatcher.ts`，模块级 Map 缓存 `ProxyAgent`，上限 50）；`validateProxyUrl` 复用 `isPrivateIpv4/6` + DNS 全地址私网拒绝 + `ALLOW_PRIVATE_UPSTREAMS` 逃生（公网代理无需开）；模型级粒度用「同 base_url 拆两个 upstream 条目」组合实现；代理不可用时 CONNECT 失败走现有重试/换 key/标记 unhealthy 逻辑
  - test-connection / fetch-models 管理端点与 upstream 创建/更新共用 `validateUpstreamBaseUrl` SSRF 校验（私网/环回/元数据地址 400），不用裸 `^https?://` 正则
  - **HTTP/HTTPS 均允许**：`baseUrl` 与 `proxyUrl` 支持本机、内网或公网的 HTTP/HTTPS；私网地址仍按 SSRF 策略拒绝，内网目标使用 `ALLOW_PRIVATE_UPSTREAMS=true`。公网明文 HTTP 会暴露链路中的 key，部署时应自行选择 HTTPS
  - **IPv6 与映射地址**：URL hostname 的方括号先剥离（`[::1]` 否则会被当成域名走 DNS）；`isPrivateIpv6` 展开 8 组后判定内嵌 IPv4，覆盖十六进制映射 `::ffff:7f00:1` / `::ffff:a00:1` / 全展开 `0:0:0:0:0:ffff:a00:1`、IPv4-compatible `::7f00:1`、NAT64 `64:ff9b::a00:1`
- **连接时 SSRF 防护（DNS rebinding 的真正解法，`src/lib/gateway/outbound-guard.ts`）**：保存时解析只代表那一刻，攻击者可让域名在真正建连时解析到 127.0.0.1/169.254.169.254。`createGuardedLookup()` 包装 `node:dns.lookup`，对**即将建连的地址**做分类（`isBlockedOutboundIp`），私网/环回/链路本地/元数据一律在 connect 前抛 `ERR_BLOCKED_OUTBOUND_ADDRESS`；`getDirectDispatcher()` 把它挂在 undici `Agent({ connect: { lookup } })` 上
- **`outboundFetch()` 是唯一出站 fetch**（`src/lib/gateway/outbound-fetch.ts`）：必须用 npm undici 自带的 fetch —— undici 8 的 Dispatcher 接口（新增 `onRequestStart`）与 Node 内建 fetch 所用的内部 undici（Node 24 = 7.29）不兼容，把 undici 8 的 `Agent`/`ProxyAgent` 传给全局 `fetch` 会抛 `UND_ERR_INVALID_ARG: invalid onRequestStart method`，**所有出站请求失败**（升级 undici 8 后实测）。因此 dispatcher 与 fetch 必须同源；单测通过 `setOutboundFetchImpl()` 注入 mock（不再 `vi.stubGlobal("fetch")`）
- **`outboundFetch` 也是运行时 URL 安全边界**：写入校验（`validateUpstreamBaseUrl` / `validateProxyUrl`）挡不住存量行、直接改库、env 覆盖，所以每次真正发请求前都执行 `assertOutboundUrlAllowed(url, scope)`（`url-guard.ts`，fail-closed）：HTTP/HTTPS 均允许；**字面 IP 不走 DNS（连接时 lookup 拦不到），在这里同步分类拒绝**（私网/环回/链路本地/元数据）；`scope` 默认 `upstream`，sync 推送传 `sync`（允许 loopback，见 `sync.md`）。内网例外统一为 `ALLOW_PRIVATE_UPSTREAMS=true`。校验失败返回 rejected promise（与 fetch 调用约定一致）
- **代理主机同样防 rebinding**：undici `ProxyAgent` 的「客户端 → 代理」连接参数是 `proxyTls`（`requestTls` 只用于隧道内已建 socket 的 TLS 升级，不再做 DNS），因此 `buildProxyAgentOptions()` 把 `createGuardedLookup()` 挂在 `proxyTls.lookup` 上；`getProxyDispatcher()` 还会先做 `assertOutboundUrlAllowed(proxyUrl, "proxy")`，存量私网字面 IP 代理在发请求时被拒，公网 HTTP/HTTPS 代理均兼容。可信代理 CONNECT 语义不变（TLS 端到端 + `redirect: "manual"`）
- **`getOutboundDispatcher(proxyUrl, { allowLoopback })` 是唯一 dispatcher 入口**（`proxy-dispatcher.ts`）：有 proxy_url → `ProxyAgent`（缓存 50 + proxyTls.lookup 校验），无 proxy_url → 受地址校验保护的共享直连 Agent（`allowLoopback` 时用 sync 专用 Agent，仅额外放行环回）。**六处带 key 出站（主链、responses 辅助链、probe、classifier、fetchUpstreamModels、fetchBalance）+ sync pusher 全部注入该 dispatcher**，不允许裸 `fetch` 直连（无 proxyUrl 时也必须有 `dispatcher`，单测断言 `toBe(getDirectDispatcher())`）
  - 日志永不打印请求 body 与任何 key

## Usage 解析器（`src/lib/gateway/parsers/`）

统一输出 `{inputTokens, outputTokens, cacheRead, cacheWrite, hasUsage}`，按协议选择：

| 字段 | OpenAI | Anthropic | Gemini |
|---|---|---|---|
| input | `usage.prompt_tokens - usage.prompt_tokens_details.cached_tokens` | `usage.input_tokens` | `usageMetadata.promptTokenCount - usageMetadata.cachedContentTokenCount` |
| output | `usage.completion_tokens` | `usage.output_tokens` | `usageMetadata.candidatesTokenCount` |
| cache_read | `prompt_tokens_details.cached_tokens` | `cache_read_input_tokens` | `cachedContentTokenCount` |
| cache_write | 0 | `cache_creation_input_tokens` | 0 |

> **统一口径**：写库字段 `input_tokens` **不含 cache_read**；`cache_read` 单独存储。OpenAI/Gemini 的原生 input 字段含 cache，parser 内部会减去 cache 部分后再写入。Anthropic 的 `input_tokens` 原生已不含 cache，无需减法。
> 展示层 Total Input = `SUM(input_tokens) + SUM(cache_read)`（含 cache），Uncached = `SUM(input_tokens)`，仅单请求（逐条记录）展示区分 uncached / cached。

## 加密（`src/lib/gateway/crypto.ts`）

- AES-256-GCM，密文格式 `iv:authTag:ciphertext`（base64）
- `GATEWAY_SECRET` 支持 hex(64) / base64(32B) / 任意字符串（sha256 派生）
- `generateVirtualKey()`：`vk-` + 32 base64url 随机字符
